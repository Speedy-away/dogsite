GTA 5 / LUA

GTA5 Lua developer references

See custom Lua UI for ListUI/ClickUI themes, native feature pages and standalone interfaces sharing built-in commands. The offline searchable API browser consumes the same generated catalog as the in-menu reference. Refresh it after changing bindings or reviewed docs:

python tools/generate_lua_developer_files.py --output build/lua-developer-files/generated
python tools/update_lua_reference_docs.py --catalog build/lua-developer-files/generated/Documentation.json --output docs/lua-api.html

The Lua workspace creates Documentation.json, DataNodes.lua and natives.lua in its Lua root automatically. The files provide editor help and are not runnable scripts. The script manager excludes their reserved filenames, the production module resolver rejects them, and the Lua files fail immediately if executed under another name. Normal scripts retain their opt-in Auto-Run settings.

Catalog and build contract

The generator tools/generate_lua_developer_files.py reads the maintained Scooby API JSON, this project's game/gta/Natives.hpp and its compiled NativeDefs.cpp wrapper table. Native definitions come from this game and build, not from another menu's wrapper file. Use natives.load_natives() once per script state before calling the named namespaces. The native capability setting still applies.

CMake generates the references and LuaDeveloperPayload.hpp under build/x64-MSVC/generated/lua-developer/. The supported wrapper stages the three reference files beside the DLL under lua-developer/. Startup installs them in the Lua folder. Missing generated files are repaired, owned files update by atomic replacement, and unrelated user files/symlinks or failed/interrupted writes preserve the old destination and report a conflict. Keep custom scripts under other names; resolve a conflict before the next startup.

The API browser uses the same generated entries and existing UI theme. JSON namespaces/members include Signature, Example, Available and native parameter information. _meta records the game and source availability basis. Availability means an exposed source binding; it does not certify a handler or behavior on every Legacy/Enhanced game version. Pointer arguments retain the native invoker's existing capability, argument and lifetime requirements.

Data-node schemas

DataNodes.lua retains the documented GTA5 raw node field schemas for editor use. These classes have no verified raw Lua bindings in this host and are marked unavailable in the JSON. They are omitted from the executable API browser. Older placeholder eSyncDataNode values are also not advertised as a verified engine contract. No constructor, arbitrary structure writer or fake successful implementation is generated from annotations. Existing compatibility globals are preserved for existing scripts. RDR2 has its own entity/native reference files and must not use GTA5 memory layouts or enum hashes.

Use the existing modular Vesper package and examples/lua/ImGuiCppDemo.lua for custom windows, callbacks and native actions. The documentation catalog and sample scripts are design/porting inputs, not an instruction to execute them or proof of unchanged cross-host compatibility.

Verification

Build with _build_run.bat (Release) or the root Visual Studio solution. The Release, Test, solution and Lua API test wrappers share a named build mutex so concurrent configure/build operations cannot replace each other's CMake scratch targets or Ninja logs. Existing toolset arguments remain supported. The ScoobyProjectRules self-test/source scan and post-link binary/map scan remain mandatory, including zero TLS callbacks and zero dynamic-CRT imports. Do not change their baselines to accept new regressions.

Run tools/test_lua_api.cmd for the existing LuaJIT/ImGui/Studio contracts plus reference installation, regeneration, custom-file preservation, interrupted replacement recovery and direct execution rejection. Production module and script-manager changes also require game acceptance. Keep evidence under build/lua-developer-files/.

The generic read-only audit tool accepts --documentation, --scripts, --host and --output. It reads every source file, hashes the inventory and reports direct call candidates without executing any code. Dynamic calls, script-defined helpers and actual return/argument behavior need further validation.

Runtime acceptance uses the exact candidate DLL for each game edition, checks reference creation, editor/browser content, normal script load/Auto-Run, module rejection, reload and shutdown, and records foreground performance per the shared guide. Build/fixture results alone do not establish game acceptance. Nothing in this workflow commits, pushes, publishes or updates changelogs.
